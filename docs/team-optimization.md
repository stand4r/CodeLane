# Подбор команды и локальное обучение

**Сейчас оптимизация команды отключена** и включается только явно:
`"ai_team_optimizer": true` в `config/settings.json`. Пока настройки нет
(по умолчанию `false`), руководитель не получает инструменты `optimize_team`
и `assess_team`, опыт команды не пишется в SQLite и блок «Оптимизация команды»
не выводится в журнал. Всё описанное ниже относится к включённому режиму.

Руководитель вызывает `optimize_team` перед распределением задач. Число `n`
включает всех исполнителей (постановку, разработку, тестирование, ревью),
но не единственного руководителя. Рекомендация не является ограничением.
Начальная оценка без анализа задачи: W=3, p=0.6, r=0.5.

Входы: W — число самостоятельных частей работы, p — доля работы, которую
можно распараллелить, r — риск. Их оценивает руководитель, поэтому прогноз
зависит от точности постановки. Для n от 1 до ceil(W):

```
H(n) = 0.04 n(n−1)/W
T(n) = (1−p) + p/n + H(n)
C(n) = 1 + 0.15n + H(n)
D(n) = min(1, r/(1+0.6(n−1)) + 0.15H(n))
J(n) = w_quality D(n) + w_time T(n) + w_cost C(n)
n* = argmin J(n)
```

T основана на законе Амдала с накладными расходами; C оценивает относительный
расход токенов; D — эвристический риск сбоя, а не измеренное качество кода.
Веса нормируются, по умолчанию 0.5/0.25/0.25. При равенстве выбирается меньшая
команда. Коэффициенты — начальные гипотезы, не экспериментально доказанные
константы. Общий оптимум времени, цены и качества одновременно не гарантирован.

Для того же проекта и endpoint/model используются последние 100 записей.
Сопоставимы задачи с объёмом в пределах ×2, разницей риска и параллельной доли
не более 0.25. Для каждого фактического размера команды предсказание
смешивается с наблюдениями: `(3 × prior + m × observed)/(3+m)`.
Расход и длительность нормируются на W и среднее сопоставимой выборки;
для D наблюдение — доля запусков с ошибками. Отмена и уточнение сохраняются,
но не считаются неудачами. Отсутствующий расход не подменяется нулём.

В SQLite рядом с кэшем команды сохраняются цель, роли, поручения, связи
родитель/ребёнок и зависимости, время, токены, ошибки, параметры модели и
оценка руководителя (`assess_team`). Последние пять разборов сопоставимых
запусков возвращаются руководителю для изменения распределения ролей.
Данные локальны; при следующем запросе эти разборы входят в контекст выбранного
API-провайдера, как и остальной контекст команды. Пароли/API-ключи специально
не сохраняются. История опыта не удаляется вместе с 14-дневными снимками.

Сохранение метрик автоматическое. Если руководитель не вызвал assess_team,
запись помечается assessment_missing; выдуманный разбор не генерируется.
Недоступность истории не блокирует работу, ошибка сохранения видна в итоге.
Подробности доступны в журнале руководителя («Оптимизация команды»).

Это обучение политики по истории, не обучение весов LLM. Самооценка руководителя
не считается доказательством качества; успешное завершение ещё не доказывает,
что код корректен. Сейчас нет автоматической оценки результатов тестов,
принятых пользователем изменений, откатов и найденных позднее дефектов.
Стоимость оценивается токенами для одной модели: тарифы, cached input и
раздельные цены output здесь не переводятся в деньги. Следующий шаг —
проверяемая обратная связь, тарифы и калибровка прогнозов по реальным запускам.
